# 0.2.1 — make the security gate tell the truth, and stop shipping a kernel header package

Status: gate reporting done in #40, toolchain purge in #41; box checks and release
pending. Not released.
Blocks: nothing. 0.2.0 is live; this is a follow-up release.

Per `AGENTS.md` §5 a published version's manifest and image are not edited, so every
change here ships as **0.2.1**.

## Done in PR #40

Scan tooling, tests and docs only — no Dockerfile, product, version or catalog change,
and existing acceptances and their 2027-01-31 expiry are unchanged.

- A single pinned Trivy 0.76.1 `--show-suppressed` scan per target yields both a
  `*.full.json` report (accepted findings retained with their statements) and a
  `*.gate.json` report (unaccepted only). No paired scans, so no tag/DB race.
- Reports go to a fresh `reports/run-*/` directory per invocation.
- `SOURCE=accepted` table and an explicit summary: unaccepted / accepted / introduced
  / deps counts.
- Warning-only checks for acceptances expiring within 30 / 7 days or expired, and for
  STALE acceptances (id not observed in the image + enabled dependency scans).
- Fail-closed: scanner errors or missing/invalid reports return 2. A report with no
  `Results` key (nothing to scan) is valid.
- The ignorefile is validated up front: each entry needs `id`, non-empty `statement`
  and a real `YYYY-MM-DD` `expiredAt`, else exit 2 before any scan. A file without
  `vulnerabilities:` is valid.
- Base attribution: with `--gate new` a base scan failure is exit 2 (attribution is
  the gate); with `--gate strict` / `none` it is a warning and the summary shows
  `introduced: n/a`.

## The problem (as found in 0.2.0)

0.2.0 shipped with `GATE PASSED — no unaccepted critical findings`
(image `ghcr.io/sh1ftred/routstrd-pro:20261110-122643-1ac542add`).

1. **The gate reported zero while the image shipped eighteen.** The scan ran with
   `--ignorefile`, so accepted findings were removed before the report was written:
   0 criticals gated vs 18 without the ignorefile. Anyone auditing `reports/*.json`
   got a false clean bill of health; during 0.2.0 review a "which accepted CVEs are
   still live" check against the gated report wrongly said all 14 had gone.
   *Fixed in PR #40.*
2. **18 acceptances are hand-copied copies of one argument.** Seventeen are
   `linux-libc-dev` with a verbatim five-line justification; one is `gosu`'s Go
   stdlib. The file format cannot express "these share one reason".
3. **All 18 expire on the same day** (`2027-01-31`): no lead time, no connection to
   the upstream fix, and eighteen decisions forced into one under release pressure.
   The kernel-header group clears when Cloudron rebuilds `cloudron/base:6.0.1` with
   Ubuntu `7.0.0-42.42`; gosu clears when it is rebuilt with Go ≥ 1.24.13. Two
   independent events, one deadline.
4. **The 17 kernel CVEs are avoidable.** `linux-libc-dev` (headers only, 1102 files
   under `/usr/include`) arrives via `libc6-dev` ← `build-essential`/`gcc`/`g++`/
   `make`, a C toolchain the base image carries and this app never uses (Bun,
   `routstrd` and the proxy are prebuilt). A throwaway image with
   `dpkg --purge --force-all linux-libc-dev` booted fine (bun, routstrd, gosu, wallet,
   `/health`, `dpkg --audit` clean) and went from 18 criticals to 1. Size unchanged
   (1.34 GB); purging the whole toolchain should shrink it but is unmeasured.
5. **The four "new" CVEs in 0.2.0 were advisory drift, not a regression.**
   `CVE-2026-74478/-74587/-74588/-74597` blocked the first 0.2.0 run against a
   byte-identical base digest: Trivy's DB gained older bugs against a package that
   already had thirteen accepted. The gate reads a live DB, so an untouched image can
   start failing on its own; the stale check above helps keep the list honest.

## Remaining work

### Collapse the rationale and stagger the deadlines

Rewrite `.trivyignore.yaml` so each *argument* appears once and ids attach to it.
Trivy takes one id per entry, so use YAML anchors:

```yaml
vulnerabilities:
  # cloudron/base:6.0.1 — linux-libc-dev: UAPI headers only (struct layouts, ioctl
  # numbers), no executable kernel code; the running kernel is the host's.
  - id: CVE-2026-89530
    statement: &uapi_reason >-
      …
    expiredAt: &uapi_expiry "2027-01-15"
  - id: CVE-2026-89652
    statement: *uapi_reason
    expiredAt: *uapi_expiry
  # … remaining kernel ids …
  - id: CVE-2025-68121        # gosu, Go stdlib crypto/tls resumption; no TLS path
    statement: >-
      …
    expiredAt: "2027-01-31"
```

Measured: wildcard ids are unsupported, `id: [A, B]` makes Trivy exit 1, anchors for
`statement`/`expiredAt` work.

| Group | Expiry | Retired by |
|---|---|---|
| linux-libc-dev (17) | **2027-01-15** | Cloudron rebuilds base 6.0.1 with `7.0.0-42.42` and we adopt its digest |
| gosu stdlib (1) | **2027-01-31** | Cloudron rebuilds gosu with Go ≥ 1.24.13 and we adopt the new digest |

Staggering turns expiry into a prompt that fails one legible group while there is
still time to act. Not doing: an `--ignore-policy` Rego rule matching all of
`linux-libc-dev` — it would silently swallow future criticals; explicit ids stay.

### Toolchain purge (PR2)

Implemented in #41: the `Dockerfile` purges the inherited compilers and header
packages (`build-essential gcc g++ cpp binutils make libc6-dev linux-libc-dev`) after
both Bun dependency installs, with `apt-get check`, an empty `dpkg --audit` and
header/tool-absence checks in the same layer. Normal apt resolution removed 45
packages — all compilers, binutils, `make`, `libtool`, `dpkg-dev` and `*-dev` header
packages; no runtime shared-library package was removed. 18 criticals → 1, so the
seventeen kernel-header acceptances are deleted rather than re-dated (the stale check
confirmed the purge first); the gosu acceptance and its expiry stay.

Two things this does not do: it removes no bytes from inherited layers, so the image
size is unchanged (1.34 GB), and the purge list names versioned packages
(`gcc-15`, `cpp-15`), which must be revisited when a base bump changes the toolchain
version — the build fails loudly on an unknown package if they are not.

Still needed: the gate showing `accepted: 1`, introduced 0, deps 0, plus a box test on
a real Cloudron (the `podman` smoke test cannot exercise the `localstorage`/`sqlite`
addons):

1. `cloudron update --app <app> --image <0.2.1 image>`; app healthy after restart.
2. Wallet initialises, `GET /health` ok, `/v1/models` returns 200.
3. Force a dashboard backup and confirm the `sqlite` addon snapshots
   `/app/data/routstrd/routstr.db` — the path a trimmed image is most likely to disturb.
4. `routstrd npubs list` and a `--limit-sats` round trip still work.

Scope: `.trivyignore.yaml`, `Dockerfile` (purge only), `CHANGELOG` `[0.2.1]` for
anything user-visible, `AGENTS.md` §7. No `src/` changes; no edits to 0.2.0's catalog
entry.

## Open questions

1. **Purge in 0.2.1, or split it?** It is the only change that reduces the finding
   count. Splitting costs two releases and two box tests; combining mixes a
   process-only change with an image change. Leaning combine — the box test is the same.
2. **Should stale acceptances fail the gate** once the count is stable (say after two
   releases)? Warn for now; the first releases will be noisy while the base turns over.
3. **Does the 90-day max need raising** for base-image findings tied to Cloudron's
   cadence? If Cloudron has not rebuilt by 2027-01-15 the right response is a new dated
   justification, not a longer one — that is the point of the date.
