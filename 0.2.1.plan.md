# 0.2.1 — make the security gate tell the truth, and stop shipping a kernel header package

Status: PR1 implemented locally; purge deferred to PR2. Not released.
Owner: —
Blocks: nothing. 0.2.0 is live; this is a follow-up release.

## PR1 implementation record

PR1 changes only scan tooling, tests and documentation. No Dockerfile, product,
version, catalog or publication changes. Existing risk acceptances and their
2027-01-31 expiry remain unchanged; this work does not renew them.

- A single pinned Trivy 0.76.1 `--show-suppressed` scan per target retains
  `Vulnerabilities` (unaccepted) and `ExperimentalModifiedFindings` (ignored,
  including Statement). The latter schema was measured locally and the derived
  gate findings compared against a regular scan on the same saved image and DB.
  There are no paired scans that could race a tag or DB update.
- Fresh per-run directories contain explicit `.full.json` / `.gate.json` reports;
  the historical `.json` filename now aliases the full report. Base/dependency
  scans also retain full reports. Full means selected severity/filter scope.
- Accepted rows show target, package, CVE and owning rationale. Counts separate
  unaccepted image, accepted image + deps, introduced, and unaccepted deps.
- Scope-aware, warning-only stale checks include image + enabled dependency scans,
  not the base. Missing observations are prompts to review, not evidence of fixes.
- UTC expiry warnings distinguish expired, within 7 days, and within 30 days.
- Mandatory scanner failures or missing/invalid reports return 2; findings return
  1 according to existing strict/new/none policy. Dependency findings still block
  all modes. Intentional `--no-deps` remains available.
- Focused fixture tests exercise suppression, schema failures, expiry boundaries,
  stale scope, strict/new/none, and missing/malformed/failed image/base/deps scans.

The design sections below are the original proposal, superseded by this record
where they describe two scans or re-dating exceptions. PR2 will separately evaluate
apt-managed toolchain removal and requires the real Cloudron box tests.

## 2. The issue

### 2.1 The gate reports zero while the image ships eighteen

`scripts/security-scan.sh` runs Trivy *with* `--ignorefile .trivyignore.yaml`, so
accepted findings are removed before the report is written. Measured on the shipped
image:

```
gated report  (reports/…-1ac542add.json)  ->  0 criticals
same image, no --ignorefile               ->  18 criticals
```

The script then prints:

```
critical findings — image: 0   introduced by this image: 0   deps: 0
```

which is accurate only under the reading "0 *unaccepted*". The report file itself is
indistinguishable from a clean image, so:

- nobody reading a release report can tell what is actually in the image;
- any later audit that reads `reports/*.json` instead of re-scanning gets a false
  clean bill of health.

This is the most important defect of the three, because it undermines every other
control. During the 0.2.0 release it produced a wrong conclusion in review: a check
of "which accepted CVEs are still live" was run against the gated report and returned
"all 14 have gone away", when in fact all 14 were present and merely filtered out.

### 2.2 The acceptances are 18 hand-copied copies of one argument

`.trivyignore.yaml` is 161 lines and 18 entries. Seventeen are `linux-libc-dev`,
each carrying a verbatim copy of the same five-line justification; the eighteenth is
`gosu`'s Go stdlib. The file format allows no way to say "these seventeen share one
reason", so the actual argument — *UAPI headers contain no executable kernel code* —
is buried in 17 repetitions and cannot be reviewed as a single decision.

### 2.3 All 18 acceptances expire on the same day

Every entry has `expiredAt: "2027-01-31"` — 82 days from the 0.2.0 release date.
Consequences:

- **No lead time.** Expiry is discovered by a release build being blocked, not by a
  warning.
- **All-or-nothing.** One date means eighteen decisions collapse into one, taken
  under time pressure on a release that is otherwise ready.
- **No connection to the fix.** The kernel-header group clears when Cloudron rebuilds
  `cloudron/base:6.0.1` with Ubuntu's `7.0.0-42.42`; gosu's `stdlib` clears when
  Cloudron rebuilds gosu with Go ≥ 1.24.13 and we adopt the new base digest. Two independent upstream events, one
  shared deadline.

### 2.4 The 17 kernel CVEs are avoidable, not inherent

`linux-libc-dev` ships `/usr/include` only (1102 files, every one a header). It
arrives as a dependency of `libc6-dev`, which arrives with `build-essential`, `gcc`,
`g++` and `make` — a full C/C++ toolchain carried by the Cloudron base image that
this app never uses. Bun, the `routstrd` daemon and the auth proxy are all prebuilt;
nothing in `start.sh`, `run-auth.sh`, `supervisord.conf`, the supervisor confs or
`docker-entrypoint.sh` invokes a compiler or `node`.

A throwaway build was made and tested (`rt-purge-test`, from the shipped image):

```dockerfile
FROM ghcr.io/sh1ftred/routstrd-pro:20261110-122643-1ac542add
USER root
RUN dpkg --purge --force-all linux-libc-dev
```

| Check | Result |
|---|---|
| `bun --version` | 1.4.4 |
| `routstrd --version` | 0.5.0 |
| `gosu cloudron:cloudron true` | ok |
| `/usr/include/linux` | gone |
| boot | wallet ready, proxy listening, `GET /health` → `{"ok":true}` |
| `dpkg --audit` | clean |
| Trivy criticals | **18 → 1** (only gosu's `stdlib`) |

So the choice on the table is 1 acceptance instead of 18, plus 17 kernel CVEs that no
longer ship. Size was unchanged at 1.34 GB in this test because only headers were
removed; purging the whole toolchain is expected to shrink the image further but was
not measured.

### 2.5 The four "new" CVEs in 0.2.0 were advisory drift, not a regression

Worth recording so the same alarm is not raised again. The first 0.2.0 gate run
blocked with `CVE-2026-74478`, `-74587`, `-74588`, `-74597`. The base image digest was
byte-identical to the one #32 shipped; Trivy's advisory database had simply gained
four entries against the same package that already had thirteen accepted ones. Their
CVE numbers (74xxx) are lower than the ones accepted in #32 (89530–98805) — older
bugs, published later.

The gate reads a live advisory DB, so **an untouched image can start failing the gate
on its own**. That is by design, but it means an expiry date is not the only way the
gate surprises you, and it is an argument for the stale-entry detection in §3.2.

## 3. The plan

Original proposed workstreams: reporting and acceptance bookkeeping, followed by
optional image trimming. PR1 implements reporting; PR2 evaluates image trimming.

### 3.1 Stop the report from hiding accepted findings

Change `scripts/security-scan.sh` to scan twice and report both numbers:

| Pass | Flags | Purpose |
|---|---|---|
| A | current flags incl. `--ignorefile` | the gate decision — unchanged semantics |
| B | same + `--show-suppressed` | the truth — every finding, with ignored ones still marked resolved |

Verified: `--show-suppressed` with an ignorefile present returns all 18 while the
gate still ignores them, so B does not weaken the gate.

Then:

- `render` gains a third table, `SOURCE=accepted`, listing each suppressed CVE, its
  package and the owning statement's subject (e.g. "linux-libc-dev / Cloudron base
  image"), so a release report answers "what is in this image" without a second scan.
- The summary line becomes explicit:
  `criticals — unaccepted: 0   accepted: 18 (17 linux-libc-dev, 1 gosu stdlib)   introduced: 0   deps: 0`
- `findings` / `NEW` / the gate decision keep using pass A, so nothing about what
  blocks a release changes.

Cost: one extra scan, ~40 s per release.

### 3.2 Detect stale acceptances

Using pass B, compare the ids present in `.trivyignore.yaml` against the ids actually
reported. Any id that no longer appears is a dead entry — print it as a warning and
keep the gate green:

```
STALE ACCEPTANCES (2) — these ids are no longer reported; remove them:
  CVE-2026-89530 (linux-libc-dev)
  CVE-2025-68121 (gosu)
```

Rationale: this is what stops the list rotting as advisories rotate and packages get
fixed. It is also the mechanism that will tell us when Cloudron rebuilds the base and
the kernel-header block can be deleted outright, instead of that block sitting there
until it expires. Warning rather than failure, because a stale entry is a
bookkeeping debt, not a release blocker.

### 3.3 Collapse the rationale and stagger the deadlines

Rewrite `.trivyignore.yaml` so that each *argument* appears once and the ids attach to
it. The format permits only one id per entry (verified below), so use YAML anchors:

```yaml
vulnerabilities:
  # ── cloudron/base:6.0.1 — linux-libc-dev (kernel UAPI headers) ─────────────
  # 1102 files, all under /usr/include: struct layouts and ioctl numbers. It
  # contains no executable kernel code, so a kernel CVE in this package cannot be
  # triggered through it; the running kernel is the Cloudron host's. Owner:
  # Cloudron base image. Clears when Cloudron rebuilds 6.0.1 with 7.0.0-42.42;
  # the stale-acceptance check in §3.2 will say when.
  - id: CVE-2026-89530
    statement: &uapi_reason >-
      …
    expiredAt: &uapi_expiry "2027-01-15"
  - id: CVE-2026-89652
    statement: *uapi_reason
    expiredAt: *uapi_expiry
  # … 15 more ids, statement/expiry anchored …

  # ── cloudron/base:6.0.1 — gosu (Go stdlib) ────────────────────────────────
  # CVE-2025-68121, crypto/tls session resumption. gosu is statically linked with
  # go1.24.6 and only drops privileges then execs; no TLS call path is reachable.
  # Owner: Cloudron base image. Clears when Cloudron rebuilds gosu with
  # Go >= 1.24.13.
  - id: CVE-2025-68121
    statement: >-
      …
    expiredAt: "2027-01-31"
```

Format findings, measured — these rule out the shortcuts:

| Attempt | Result |
|---|---|
| `id: CVE-2026-744*` (wildcard) | not supported — 18 findings still reported |
| `id: [CVE-A, CVE-B]` (list) | rejected — Trivy exits 1, invalid ignorefile |
| `statement: &a` / `*a` anchors | works — 2 ids shared one statement and expiry |

Staggered expiries, each tied to the upstream action that retires it:

| Group | Expiry | Retired by |
|---|---|---|
| linux-libc-dev (17) | **2027-01-15** | Cloudron rebuilds base 6.0.1 with Ubuntu `7.0.0-42.42` and we adopt its digest |
| gosu stdlib (1) | **2027-01-31** | Cloudron rebuilds gosu with Go ≥ 1.24.13 and we adopt the new base digest |

Keeping the earlier one inside the 90-day policy but ahead of the rest means the
expiry works as a prompt: it fails one legible group while there is still time to act,
rather than blocking eighteen entries at once.

Deliberately **not** doing: an `--ignore-policy` Rego rule that ignores every critical
matching `linux-libc-dev`. It would achieve a literal one-entry file, but a rule
matching a whole package silently swallows any future critical in it — strictly worse
than explicit ids, which the stale-entry check can audit. Explicit ids stay.

### 3.4 If the purge is taken (§2.4), it changes the file again

Two options; recommend **both**, in this order, as one release:

- **3.4a** Land §3.1–3.3 alone. Ships no image change beyond the scan script, and is
  the safest possible 0.2.1.
- **3.4b** Additionally purge the unused toolchain in the `Dockerfile`:
  `build-essential gcc g++ make libc6-dev linux-libc-dev` (libc6-dev is what actually
  pulls the headers). This takes the image from 18 criticals to 1 and lets seventeen
  of the acceptances be deleted rather than re-dated. Requires the box test in §5.

If 3.4b is taken, §3.3's kernel-header block is deleted instead of re-dated — the
stale-entry check from §3.2 will confirm the purge worked.

## 6. Open questions

1. **Take §3.4b (purge) in 0.2.1, or split it?** Purge is the only change that reduces
   the finding count. Splitting it means two releases and two box tests; combining it
   risks mixing a process-only change with an image change. Recommendation: combine,
   because the box test is the same test.
2. **Should stale acceptances fail the gate** once the count is stable (say after two
   releases), rather than warn? Warning now, revisit later — the first releases will be
   noisy while the base image turns over.
3. **Does the `.trivyignore.yaml` expiry policy (max 90 days) need raising** for
   base-image findings that depend on Cloudron's release cadence? The originally proposed April gosu date was outside 90 days from the November
   release context and has been corrected; PR1 keeps existing dates, not new approvals. If Cloudron has not rebuilt by 2027-01-15, the correct response is
   a new dated justification, not a longer one — that is the point of the date.
4. **`github.com/Routstr/routstr-sdk` 0.5.1 and `routstrd` 0.5.0 bundling** are
   untouched by this release; no dependency work is needed here.
